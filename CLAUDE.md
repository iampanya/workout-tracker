@AGENTS.md

## Commands

```bash
npm run dev                                          # dev server
npm test                                              # pure-function unit tests, no DB needed
DOTENV_CONFIG_PATH=.env.local npm run test:db         # DB-backed integration tests (needs `supabase start` running)
npx tsc --noEmit && npm run lint                      # typecheck + lint
```

Full local setup (Supabase CLI, `.env.local`, creating the one user account) and deployment steps are in `README.md` — read it before first-time setup.

## Architecture

- `app/(app)/**/page.tsx` — server components; fetch via the Supabase server client, pass data to client components.
- `lib/actions/*.ts` — thin `"use server"` wrappers: resolve `userId`, call a `lib/<domain>/service.ts` function, `revalidatePath`.
- `lib/<domain>/service.ts` — the actual business logic, as plain functions taking `(supabase, userId, ...args)`. Call these directly in tests — no mocking needed, since DB-backed tests (`lib/**/*.test.ts`, run via `test:db`) hit a real local Supabase instance via `lib/supabase/test-helpers.ts`.
- `components/ui/{Button,Card,IconButton,Input,Select,Badge,StatCard,NumberField,ConfirmDialog,ExerciseCombobox}.tsx` — the design-system primitives; reuse these rather than raw Tailwind for new screens. `Input`/`Select` take a separate `wrapperClassName` prop for layout sizing (flex/width) — `className` only reaches the inner `<input>`/`<select>`. `ConfirmDialog` is the standard destructive-action modal (overlay + autofocused confirm); use it for any immediate delete. `ExerciseCombobox` is the searchable exercise picker (filters by name **or** `muscle_group`); it expects `exercises` pre-sorted by muscle_group then name (as `listExercises` returns) so it can group results.
- No component-level (`.tsx`) test harness exists. UI behavior is verified manually in the browser, not with automated component tests.

## Gotchas

- This is a **multi-user, invite-gated app**. Login is by **username**, not email (`app/login/page.tsx` → `loginWithUsername`); a `profiles` row maps username→auth user, and all data tables are already isolated per user via RLS (`user_id = auth.uid()`). Signup (`app/signup/page.tsx` → `signup`) requires a valid **referral code**. Supabase's public `enable_signup` stays **false** by design — accounts are minted server-side via the service-role admin API (`lib/auth/service.ts::createUserWithReferral`), never by client self-serve signup.
- **Referral codes (invites).** Every user owns **one permanent, personal `profiles.referral_code`** (8-char, `not null unique`, generated by `gen_referral_code()` in `0004_referral_codes.sql` and mirrored app-side by `generateReferralCode()` in `lib/referrals/service.ts` — keep the two alphabets in sync). It's **multi-use, no expiry**: unlimited people can sign up with the link `/signup?invite=<CODE>` (the signup page prefills + read-only-locks the field when `?invite=` is present). `createUserWithReferral` looks up the inviter by referral code, and records `profiles.referred_by` on the new account. The safety valve for a leaked code is **regenerate** (`regenerateReferralCodeAction` → `regenerateReferralCode`), surfaced on the **Profile** page (`app/(app)/profile/ReferralCard.tsx`) alongside a Copy button and an "Invited N friends" count. That count comes from the **`referral_count()` SECURITY DEFINER RPC** — `profiles_select_own` RLS hides invitees' rows, so the definer function returns only an aggregate integer (never widen it to return rows). The old single-use `invite_codes` table was **dropped** in `0004`. The first account can't be referred by anyone, so it's bootstrapped by inserting a `profiles` row directly (see `README.md`).
- Auth gating happens in **`proxy.ts`** (Next 16's renamed `middleware.ts`, not `middleware.ts`) → `updateSession` in `lib/supabase/middleware.ts`, which redirects any route **not** in `PUBLIC_ROUTES` to `/login` when there's no user — this runs *before* any `page.tsx`. So making a page reachable while logged out means adding its path to `PUBLIC_ROUTES` (currently `/`, `/login`, `/signup`); a page-level auth check alone is never reached. `/` is the public landing (`app/page.tsx` renders `components/landing/LandingPage.tsx` when logged out, and `redirect("/dashboard")` when logged in). The landing nav reuses the compact `components/theme/ThemeToggleButton.tsx` (the in-app `TopBar` no longer uses it — Settings and the in-app account menu both use the segmented `ThemeModeControl`); all share the `ThemeProvider` store.
- Identity resolution on the **navigation path** (middleware + every `page.tsx`/`layout.tsx`) uses **`supabase.auth.getClaims()`, not `getUser()`** — `getClaims` verifies the session JWT **locally** (no round trip to the Supabase Auth server), which is the single biggest server-latency win when Supabase is a region away. This **only works with asymmetric JWT signing keys (ECC/RS)**: on the legacy symmetric HS256 secret, `getClaims` *silently falls back to `getUser()`* (a network call) — so it's a no-op unless the project has migrated its signing keys (prod has; **local Supabase is HS256, so you won't see the speedup locally**, only correct behavior). Pages/layouts call the shared `getAuthUser()` in `lib/supabase/auth.ts` (returns `{ id, email } | null`), which is `cache()`-wrapped so layout + page verify **once** per render instead of twice. Middleware calls `getClaims()` inline (it uses the request/response cookie adapter, not `next/headers`, so it can't use `getAuthUser`); `getClaims` still refreshes an expired-but-refreshable token and writes rotated cookies, preserving middleware's refresh duty. **Deliberate exception: the 4 `getUser()` calls in `lib/actions/*` stay `getUser()`** — mutations aren't on the nav path (fire on submit, not per page load), and `getUser` keeps them revocation-tight (a signed-out/banned session can't mutate for up to the access-token TTL). JWKs are cached process-globally (`GLOBAL_JWKS` in auth-js), so the public key is fetched once per cold start, not per request.
- The in-app top bar (`app/(app)/TopBar.tsx`) is a sticky, `border-b`, `backdrop-blur` header whose contents are centered in a `max-w-5xl` container (matching `<main>`). It is **responsive**: on mobile it shows the brand mark (top-level routes) or a back button (sub-pages) on the left and the `AccountMenu` on the right, with the fixed `BottomNav` as the primary nav; on desktop (`lg:`) it *also* renders horizontal nav links plus a primary "Log workout" link inline, and `BottomNav` is hidden (`lg:hidden`). The 4 nav items live in the shared `app/(app)/nav-items.ts` (imported by both `TopBar` and `BottomNav` — edit there, not in each). The right-side `AccountMenu` (`app/(app)/AccountMenu.tsx`) is a username-triggered dropdown (`aria-haspopup="menu"`, closes on click-outside/Escape) holding Profile, Settings, an inline `ThemeModeControl`, and Log out. Profile lives at its own route `app/(app)/profile/page.tsx` (username + `user.email` + member since); Settings is Appearance + Account only. Both are sub-pages (not in `TOP_LEVEL_ROUTES`), so the back button appears there on mobile. `TopBar` needs both `user.email` and `resumeSessionId` (for the "Log workout" link's resume target) passed down from `app/(app)/layout.tsx`; page content is width-capped by `<main className="mx-auto w-full max-w-5xl ...">` there — `lg:` is the desktop breakpoint used app-wide.
- Destructive/blocking flows use the shared `components/ui/ConfirmDialog.tsx` modal, never inline confirms: Log out (both the account menu and Settings' `LogoutButton`), Discard workout, and Remove exercise all open a `tone="danger"` confirm. Pass `hideCancel` to turn `ConfirmDialog` into a single-button alert — the Finish-workout guard uses this (title "Can't finish yet", button "Got it") instead of a top text banner; it still highlights empty exercise cards with a red ring as an extra cue.
- `ConfirmDialog` renders its overlay through a React portal to `document.body` (`createPortal`) and locks body scroll while open. The portal is **required, not cosmetic**: the dialog is invoked from inside `TopBar` (the account-menu Log out), whose `backdrop-blur` establishes a containing block that traps `position: fixed` — without the portal, `fixed inset-0` resolves against the ~56px bar and the modal overflows off the top of the screen instead of centering. Don't revert it to inline rendering.
- The service-role admin client (`lib/supabase/admin.ts`) bypasses RLS and must be imported **only** from `"use server"` modules (currently just `lib/actions/auth.ts`). `SUPABASE_SERVICE_ROLE_KEY` is server-only (never `NEXT_PUBLIC_*`) and must be set in the deploy env (Vercel). The username→email resolution at login (`getEmailForUsername`) runs through this client server-side so emails are never exposed to the browser (no username enumeration); login failures always return one generic error.
- RLS is not automatically enough on its own: `session_exercises`' RLS policy only checks the *inserted* row's own `user_id`, not that the referenced `session_id` actually belongs to that user. Service functions that insert child rows under a parent the caller doesn't own need an explicit ownership check first (see `addExerciseToSessionForUser` in `lib/sessions/service.ts`).
- `exercise_prs` is a live Postgres view (`max(weight_kg)` per user+exercise, excluding warmup sets), not a cached table — never denormalize/cache its value. It requires `security_invoker = true` to run under the querying role's RLS instead of the view owner's (superuser) privileges — see the comment in `supabase/migrations/0001_init.sql`.
- Set numbering uses `max(set_number) + 1`, never `count(*) + 1` — deleting a set from the middle leaves a gap, and `count(*)` would recompute a number that collides with the `unique(session_exercise_id, set_number)` constraint.
- All weights are stored and displayed in kilograms — no unit conversion anywhere in the app.
- A session's display label is `session.name ?? routine?.name ?? "Freeform Workout"` via `sessionDisplayName` in `lib/sessions/history.ts`. The routine name is **snapshotted** into `sessions.name` at start (`StartSessionButtons` passes it), so a later routine rename/delete doesn't rewrite history; the `routine:routines(name)` join is only a fallback for pre-snapshot rows. Any query that displays a session must select that join (see `listCompletedSessions`, `listInProgressSessions`, `getSessionDetail`, and the log page).
- `finishSessionForUser` requires a session to have **at least one logged set** before it can complete — it rejects both a session with **no exercises at all** ("Add at least one exercise with a logged set before finishing") and one where any `session_exercise` has zero `sets` ("Remove exercises with no sets before finishing"). The client (`LoggingClient`) blocks both cases too (empty-workout warning + highlights empty exercises), but the server guard is the source of truth.
- `exercise_prs` is a view without FK metadata, so PostgREST embeds like `exercises(name)` don't resolve against it — fetch exercise names in a second `exercises` query keyed by `exercise_id` (see `listTopPrs`/`listPrsFromLastCompletedSession` in `lib/dashboard/service.ts`).
- Icons come from `@phosphor-icons/react` — always import from the `/ssr` subpath (`@phosphor-icons/react/ssr`), even in Client Components. The default entrypoint's icon base calls `useContext`, which crashes when the component tree is rendered from a Server Component (most `app/(app)/**/page.tsx` files are).
- Stepper-style +/- controls must compute their next value inside the parent's functional `setState` updater, not from a prop closed over at render time — React batches rapid taps, and reading a stale prop silently drops all but one tap. See `applyStep` in `components/ui/NumberField.tsx` and its callers in `LoggingClient.tsx`.
- After adding/removing an npm dependency, kill the running `next dev` process and `rm -rf .next` before restarting — Turbopack's HMR can keep serving a stale chunk referencing a removed package, throwing a runtime `ReferenceError` even with `tsc`/lint clean.
- To QA authenticated flows locally without the real account's password: create/delete a throwaway user via the GoTrue admin API using `SUPABASE_SERVICE_ROLE_KEY` from `.env.local` (`POST`/`DELETE` `$NEXT_PUBLIC_SUPABASE_URL/auth/v1/admin/users`).
