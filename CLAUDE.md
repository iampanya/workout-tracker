@AGENTS.md

## Commands

```bash
npm run dev                                          # dev server
npm test                                              # pure-function unit tests, no DB needed
DOTENV_CONFIG_PATH=.env.local npm run test:db         # DB-backed tests (needs local Docker Postgres migrated)
npm run db:reset                                      # prisma migrate reset + seed presets (local dev)
npm run db:migrate                                    # prisma migrate deploy (non-destructive apply)
npx tsc --noEmit && npm run lint                      # typecheck + lint
```

Full local setup (Docker Postgres + a `workout_tracker_dev` db/role, `.env`/`.env.local`, Google OAuth client) and deployment are in `README.md` / `docs/DEPLOY.md` — read them before first-time setup.

## Architecture

- **Stack:** Next.js 16.3 + **Prisma** (Postgres, direct connection) + **Auth.js / NextAuth v5** (Google sign-in). The app uses **no `@supabase/*` package** — Supabase (or any Postgres) is just the DB host, reached via `DATABASE_URL`.
- `app/(app)/**/page.tsx` — server components; resolve the user with `getAuthUser()` (`lib/session.ts`), fetch via the Prisma client (`lib/db.ts`), pass data to client components.
- `lib/actions/*.ts` — thin `"use server"` wrappers: `requireUserId()` (`lib/session.ts`), call a `lib/<domain>/service.ts` function with `prisma`, `revalidatePath`.
- `lib/<domain>/service.ts` — business logic as plain functions taking `(db, userId, ...args)` where `db` is a `PrismaClient`. Call these directly in tests — DB-backed tests (`lib/**/*.test.ts`, run via `test:db`) hit a real local Postgres; `lib/test-helpers.ts::createTestUser()` inserts a `public.users` row via Prisma (the `on_public_user_created` trigger provisions the profile).
- `components/ui/{Button,Card,IconButton,Input,Select,Badge,StatCard,NumberField,ConfirmDialog,ExerciseCombobox}.tsx` — design-system primitives; reuse these rather than raw Tailwind. `Input`/`Select` take a separate `wrapperClassName` prop for layout sizing (flex/width) — `className` only reaches the inner element. `ConfirmDialog` is the standard destructive-action modal (overlay + autofocused confirm). `ExerciseCombobox` filters by name **or** `muscle_group` and expects `exercises` pre-sorted by muscle_group then name (as `listExercises` returns).
- No component-level (`.tsx`) test harness exists. UI behavior is verified manually in the browser.

## Gotchas

- **Auth is Auth.js (NextAuth v5), Google-only, open signup.** Config is split: `auth.config.ts` (edge-safe, no adapter — used by `proxy.ts` middleware) and `auth.ts` (full: Prisma adapter + JWT sessions). Google uses `allowDangerousEmailAccountLinking` so a sign-in links to an existing `public.users` row with the same email (how GoTrue-migrated users keep their data). First login auto-creates the profile — there is no bootstrap/invite step. `signIn`/`signOut` in client components come from `next-auth/react`.
- **Per-user isolation is enforced in the service layer, NOT RLS** (RLS was disabled in `0010`; the app connects to Postgres directly, bypassing it). Every service query MUST filter by `user_id`, and any function that inserts a child row under a parent must first verify the caller owns that parent (see `addExerciseToSessionForUser`/`addExerciseToRoutineForUser`). A forgotten `where user_id` = a cross-user leak — so each service has cross-user **isolation tests** (e.g. `lib/exercises/service.test.ts`); keep that pattern when adding services.
- **Route gating is in `proxy.ts`** (Next 16's renamed `middleware.ts`) via `NextAuth(authConfig).auth(...)` + helpers in `lib/routes.ts`. `PUBLIC_ROUTES` = `/`, `/login`; `/login` is guest-only (logged-in → `/dashboard`); the matcher excludes `/api/auth/*` (Auth.js routes) and static assets. Make a page reachable while logged out by adding it to `PUBLIC_ROUTES`. `/` is the public landing (`app/page.tsx` → `components/landing/LandingPage.tsx`, passes `authed` so CTAs adapt; does not redirect).
- **Identity:** `getAuthUser()` (`lib/session.ts`) wraps Auth.js `auth()` (JWT verified locally, `cache()`-wrapped so layout + page verify once) and returns `{ id, email } | null`; `requireUserId()` throws for mutations. Don't reach for a Supabase client — it's gone.
- **Prisma is the client only; DB objects live in SQL migrations.** The `exercise_prs` view, `import_backup`/`gen_referral_code`/`handle_new_user` functions, and triggers are raw SQL inside the migration files, not the Prisma schema. `prisma/schema.prisma` is **public-schema-only** and kept in sync with `prisma db pull` (don't hand-add the view — read it via `$queryRaw`). Prisma 7 puts connection URLs in `prisma.config.ts` (not the schema) and the runtime client uses the pg driver adapter in `lib/db.ts`.
- **Prisma Migrate is the single source of truth for schema — local AND prod (baselined 2026-09-15; see `docs/adr/0001-local-db-on-docker-postgres.md`).** The baseline is one squashed vanilla-PG migration `prisma/migrations/0001_init/migration.sql` (no `auth` schema / Supabase roles / RLS / `auth.uid()`). Prod was adopted onto it with `prisma migrate resolve --applied 0001_init`. **Change the schema:** `prisma migrate dev --name <x>` (local) → `DIRECT_URL=<prod> npx prisma migrate deploy` (prod, before deploying code — never in the Vercel build). Non-model objects (view `exercise_prs`, functions, triggers) aren't in `schema.prisma`, so hand-write their SQL into the generated migration, then `prisma db pull` to resync. `supabase/migrations/*.sql` is **archived legacy** (the old GoTrue/Supabase chain, no longer applied — see `supabase/README.md`); don't add to it. The seed (preset exercises) lives in `supabase/seed.sql`, run by `prisma/seed.mjs` (single source of the preset list).
- **Local-dev migration quirks (Prisma 7).** `npm run db:reset` = `prisma migrate reset --force && prisma db seed` — reset does **not** auto-run the seed in Prisma 7, so it's chained. Prisma also **refuses `migrate reset` when an AI agent runs it**; rerun with `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION="<user's exact consent text>"` and only after the user explicitly consents (it wipes the target DB — dev only). When regenerating `prisma/migrations/0001_init` from `pg_dump`, **delete the `SELECT pg_catalog.set_config('search_path','',false)` line** — an empty search_path hides Prisma's `_prisma_migrations` table and fails the apply.
- **Env:** the Prisma CLI reads `.env`, Next reads `.env.local` — keep `DATABASE_URL`/`DIRECT_URL` in **both**. In prod `DATABASE_URL` must be a **pooled** connection (Supavisor :6543, `?pgbouncer=true&connection_limit=1`) for serverless; `DIRECT_URL` (:5432) is for migrations. `prisma.config.ts` reads `process.env.DIRECT_URL ?? process.env.DATABASE_URL` (plain env, not prisma's `env()`) so `prisma generate` in Vercel's postinstall doesn't hard-fail when `DIRECT_URL` is unset. Auth.js needs `AUTH_SECRET` + `GOOGLE_CLIENT_ID`/`GOOGLE_SECRET` (set all of these in Vercel Production too).
- **Postgres `numeric` → Prisma `Decimal`:** coerce `weight_kg` with `Number()` before returning to the UI (see `toSetRow` in `lib/sessions/service.ts`). Prisma returns timestamps as `Date` — serialize to ISO/`YYYY-MM-DD` strings where a consumer expects a string (see `serializeSession`/`toCompletedSession`).
- **Referral codes still exist but no longer gate anything** (signup is open). Every profile has a personal `referral_code` (`gen_referral_code()` in `0004`, mirrored by `generateReferralCode()` in `lib/referrals/service.ts` — keep alphabets in sync), shown on the Profile page with a regenerate button; `getReferralInfo` counts invitees with a plain `count(referred_by = userId)` (the old `referral_count()` RPC is unused). The invite-link/`/signup` flow was removed.
- Set numbering uses `max(set_number) + 1`, never `count(*) + 1` — deleting a middle set leaves a gap, and `count(*)` would collide with `unique(session_exercise_id, set_number)`. Same rule for `position` on routine/session exercises.
- A session's display label is `session.name ?? routine?.name ?? "Freeform Workout"` via `sessionDisplayName` in `lib/sessions/history.ts`. The routine name is **snapshotted** into `sessions.name` at start, so a later rename/delete doesn't rewrite history; the Prisma `include: { routines: { select: { name } } }` is only a fallback for pre-snapshot rows.
- `finishSessionForUser` requires **at least one logged set** — rejects a session with no exercises ("Add at least one exercise with a logged set before finishing") or one where any `session_exercise` has zero sets ("Remove exercises with no sets before finishing"). The client blocks both too, but the server guard is the source of truth.
- `import_backup` has a portable overload `(payload, mode, p_user_id)` (`0009`) that takes the user id instead of `auth.uid()`; `lib/backup/service.ts` calls it via `$queryRaw`. Extend the JSON backup by adding tables to `exportUserData` + `ImportSummary` and to `import_backup` (FK-safe deletes; remap ids on global collision).
- Destructive/blocking flows use `components/ui/ConfirmDialog.tsx` (never inline confirms): Log out, Discard workout, Remove exercise. It renders through a `createPortal` to `document.body` (required — invoked from inside `TopBar`'s `backdrop-blur`, which would trap `position: fixed`; don't revert to inline). `hideCancel` turns it into a single-button alert (the Finish-workout guard).
- All weights are stored and displayed in kilograms — no unit conversion anywhere.
- Icons come from `@phosphor-icons/react` — always import from `@phosphor-icons/react/ssr`, even in Client Components (the default entrypoint calls `useContext` and crashes when rendered from a Server Component).
- Stepper +/- controls must compute the next value inside the parent's functional `setState` updater, not from a prop closed over at render (React batches rapid taps; a stale prop drops all but one). See `applyStep` in `components/ui/NumberField.tsx`.
- After adding/removing an npm dependency, kill `next dev` and `rm -rf .next` before restarting — Turbopack HMR serves stale chunks referencing a removed package, throwing a runtime `ReferenceError` even with `tsc`/lint clean.
- To QA authenticated flows locally you must **sign in with Google** (no password path exists). For DB-level test data, create users with `createTestUser()` (`lib/test-helpers.ts`) — the trigger provisions the profile.
